01 / SYSTEM DESIGN

A small Core.
An adaptive NIX.

Recommended design: a capability-based microkernel with system services in user space. OpenCode supplies the local coding-agent engine behind NIX’s intent broker. The AI proposes and assembles experiences; deterministic services enforce permissions and execute approved plans. Generated code never rewrites the running kernel.

01
Intent shellRUST · USER SPACE

One prompt by default. No desktop, icons, or terminal unless requested. A compositor presents the task interface when needed. Author, Wallet, and Play remain named capabilities accessible through the prompt. Asking for a desktop reveals optional icons; asking for a terminal opens an explicitly requested command environment. Deterministic input and recovery remain available without inference.

02
Local intelligenceRUST ORCHESTRATOR · LOCAL RUNTIME

Intent understanding, questions, research synthesis, planning, code generation, and local retrieval run on the machine. Models execute in unprivileged processes. CPU inference is the baseline; GPU acceleration requires supported compute drivers.

03
Policy & executionRUST · CAPABILITY BROKER

Convert model output into typed, validated plans. Separate proposal, user decision, and execution. Limit tools, resources, network access, and Memory access per task. Retrieved text has no authority to grant permissions.

04
NIX servicesRUST · ISOLATED SERVICES

Memories, package research, builds, Pod lifecycle, networking, compositor, audio, device discovery, secrets, and signed updates communicate through versioned IPC protocols.

05
Core kernelRUST NO_STD · C / SMALL ASM BOUNDARIES

Boot handoff, physical and virtual memory, threads, scheduling, interrupts, IPC, capabilities, clocks, and isolation. Use Rust by default; audit unsafe code and reserve C for required interfaces or selected low-level components.

06
Hardware boundaryCUSTOM X86-64 · UEFI

A narrow, certified hardware profile. UEFI loader, ACPI discovery, PCIe enumeration, IOMMU isolation, USB input, storage, networking, and display drivers form the foundation. Hardware selection precedes broad compatibility promises.

LOCAL SOFTWARE ENGINE / OPENCODE

NIX is the interface.
OpenCode is the coding engine.

Integration specification: NIX connects a custom prompt-first client to a local, headless OpenCode service. Local Qwen inference supplies reasoning and code generation. Core and NIX services retain authority over devices, Memories, permissions, and deployment.

Refactor the experience; preserve the engine boundary.

Maintain a NIX client and adapter with minimal changes to OpenCode internals. Pin a release and its API schema, retain a patch ledger, and test session creation, event streaming, cancellation, tool errors, and upgrade compatibility. Refactor or fork engine internals only when an adapter cannot meet the contract.

Memories adapter

Proposed NIX tools: memory.search, memory.read, memory.stage_write, and memory.commit. These are NIX interfaces, not stock OpenCode endpoints. Map only approved Memories into the agent’s working directory. Commit changes through versioned receipts; never mount the full personal store.

Pod adapter

Proposed NIX tools: catalog.search, research.fetch, build.run, pod.propose, pod.install, and pod.rollback. Builds receive restricted source and dependency access. Installation is executed by the trusted broker after policy checks, separate from the agent workspace.

Intent execution contract

Understand → Ask → Research → Select → Build if needed → Verify → Deploy → Open. Every transition has an intent ID and a recorded result. Existing software is evaluated first. A failed build stays inside its Pod; a cancelled task cannot publish a late artifact. Installation uses immutable artifact hashes and a rollback receipt.

Example: “I want to write a book.”

NIX asks whether a manuscript exists. The broker creates a scoped OpenCode task, checks the approved software catalog, and compares reusable editors. If adaptation or new code is required, OpenCode works in a build workspace, runs checks, and returns an artifact and permissions manifest. The broker deploys Author and opens its writing interface. Manuscripts are Memories; desktop icons are optional.

Local operation and network control

All inference runs on the computer. Research and package retrieval use a separate, permission-controlled egress service. Deny other service-Pod egress, disable sharing and unnecessary update checks, and audit plugins and model metadata requests. An offline acceptance run must complete a cached research/build task with external networking blocked.

Runtime and release gates

OpenCode’s runtime dependencies run inside the Linux service guest. This requires Core’s VM support first; a development host can validate the adapter separately. Native execution on Core requires porting the runtime, process, filesystem, networking, and toolchain dependencies. A new UI alone does not supply native-kernel compatibility.

Acceptance gates: local-only inference verified by network capture; unrelated Memories inaccessible; builds cannot install directly; cancellation stops tool work; crashes preserve committed content; rollback restores the previous artifact; desktop and terminal remain absent until explicitly requested.

This website documents the integration contract and contains scripted interface examples. The ZIP contains the website, not OpenCode binaries, model weights, a kernel image, or an operational agent backend.

Primary implementation references: OpenCode server, SDK, local model configuration, and upstream license. Retain the license and notices required by the pinned release and audit redistributed dependencies.

03 / SOFTWARE ISOLATION

One intent.
The right Pod underneath.

A Pod is NIX’s application deployment unit: an artifact, runtime or guest image, permissions, resource limits, data mounts, and a launch recipe. “Pod” is a NIX abstraction; Linux containers cannot run directly on a new kernel without the required runtime and system-call support.

Pod typeExecution pathScope and dependencies
NativeNIX executable or a ported WebAssembly runtimeNew tools target the NIX ABI/SDK. WebAssembly requires a supported host runtime and explicitly exposed capabilities.
CompatibilityPorted API/runtime layerPer-application validation. Wine-like tooling needs substantial OS interfaces and graphics support; it is not a universal Windows switch.
Virtual machineWindows or Linux guest in an app-scoped VMCore virtualization primitives and a user-space VMM/device model. Licensed guest media and application installers. Window integration presents the requested application directly, with an optional desktop.
EmulatedCPU and device emulation in a ported runtimeFallback for unsupported architectures or old hardware assumptions. Higher overhead; test graphics, audio, timing, and input individually.

Legacy example: “I want to play Freelancer.”

Research the exact edition and installer first. Select a tested guest configuration, request legal installation media and any required license, then create a dedicated Windows Pod. Install the game, configure graphics/input/audio, verify launch, and register Freelancer for prompt launch, with an icon only on a requested desktop. The guest OS remains an implementation detail with an accessible management view.

Compatibility is a test result, never a blanket guarantee. Diablo needs edition-specific research, launcher support, GPU drivers, and any online-service or anti-cheat requirements. GPU passthrough requires IOMMU support and a compatible device allocation; a separate host display adapter may be needed.

Pod manifest contract

id artifact_hash runtime entrypoint memory_refs capabilities network_policy cpu_ram_gpu_limits license_refs rollback_version

Read-only base images, writable app overlays, explicit Memory mounts, and mediated device access. Uninstall removes the runtime and task registration while offering a separate choice for user-created Memories.

04 / PERSISTENT STATE

Your files are Memories.

Documents, books, photos, audio, films, game installations, and saved projects are presented as Memories. The model’s conversational context is a separate, explicitly labeled subset.

Object store underneath

Each Memory has a stable ID, typed content, ownership, timestamps, versions, provenance, and access grants. Binary blobs live in a persistent filesystem-backed store; a transactional metadata index handles names, relationships, and search. Embeddings are derived indexes that can be rebuilt.

Use separate classes for personal creations, installed software assets, game saves, task history, and AI preferences. This keeps “uninstall game” distinct from “delete my saves.”

A bridge to existing apps

The Memory broker exposes selected objects as ordinary paths inside each Pod. Save operations create versions. Mounts can be read-only, read-write, or one-time imports; apps cannot browse all Memories by default.

Provide export to normal directories, encrypted local backup and restore, explicit deletion with retention controls, and key recovery choices. Persist the metadata and content before marking a save complete.

Prefer restartable user-space drivers where practical. Core retains privileged interrupt and memory-mapping primitives; the driver broker grants narrow MMIO, IRQ, and DMA capabilities. DMA isolation requires configured IOMMU mappings.

UEFI boot drivers do not replace runtime storage, networking, USB, or GPU drivers after the OS takes over. Existing Linux/Windows drivers require porting or a guest path. A basic framebuffer can display the first prompt; accelerated AI, games, and XR need a separate driver effort.

06 / LOCAL AI & ACTIVE UX

The model proposes.
NIX carries it through.

Model service

Ship the local model weights and inference runtime as required system components. The base image includes Core, essential drivers, services, prompt shell, compositor, recovery tools, and AI. Consumer applications are installed on demand.

Use a local model registry with hashes, versioned prompts, context limits, and a resource governor. Preempt or pause heavy inference during gaming and XR. Model weight size, RAM/VRAM, disk requirements, and latency targets must be measured on the selected hardware before a minimum specification is published.

Active without taking over

NIX can ask “Do you have an existing manuscript?” or suggest a chapter outline. It can surface a missing dependency and explain the proposed install. Suggestions stay tied to the current intent and can be dismissed or disabled.

Retain deterministic launch, save, close, recovery, and settings paths if the model fails. Kernel updates follow a signed build/review pipeline and reboot activation; the AI does not hot-patch the trusted foundation.

Bitcoin Wallet: research and integrate a maintained wallet implementation first. Keep seed phrases and private keys outside model context, logs, and build Pods. Use a separate secrets/signing service, established cryptography, explicit transaction review, and independent security evaluation before handling real funds. A generated interface is not a validated wallet.

08 / NEXT DESIGN QUESTIONS

The foundations are settled.
These choices come next.

Which exact custom x64 computer is the first target?

Choose one CPU platform and one GPU model, plus storage, network, audio, and USB controllers. Decide whether a second GPU will be available for guest passthrough. This fixes the initial driver scope.

Can NIX browse the internet for research?

Recommendation: offline by default, with explicit network permission per research or installation task. All AI computation remains local in either mode.

Should Core use the proposed microkernel design?

Recommendation: a small capability-based kernel, with user-space drivers and services where practical. Confirm this architectural proposal before freezing the kernel ABI.

What should NIX prove first?

Recommendation: Author. A writing workspace proves intent, interface assembly, native Pods, Memories, and persistence without the immediate GPU and guest-OS dependencies of gaming.

How should NIX change its own interface?

Recommendation: compose vetted UI primitives first. Generated code stays inside build/application Pods, with permission review and rollback. Core remains a separately built and signed component.
